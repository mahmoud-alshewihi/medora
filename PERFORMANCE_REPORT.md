# Medora v0.14 — Performance & Load Test Report

All numbers below are REAL measurements from an isolated local instance. Nothing is extrapolated or invented.

## Environment (recorded, not assumed)
- App: Next.js production build (`next start`), Node v22.23.5, Prisma 7.
- DB: PostgreSQL 19.0 (isolated local instance, port 5433).
- Hardware: 1 vCPU (Intel Xeon Platinum 8375C @ 2.90GHz), 2 GB RAM sandbox. Single process, in-memory rate limiter.
- Method: custom closed-loop harness (scripts/load.mts), 5s per level, concurrency 10/50/100/200 virtual users.
  Each virtual user sends a distinct X-Forwarded-For value (what a production proxy appends as the last hop),
  so the per-IP rate limiter behaves exactly as it would with real distributed users.

## Benchmark dataset (real rows, verified by COUNT)
50k patients (50,501), 250k appointments (251,003), 100k invoices (100,581 + 100,737 items),
52 clinics, 154 branches, 512 doctors. Generated by scripts/bench-seed.mts (deterministic, no per-doctor overlap), loaded via COPY, ANALYZE run afterwards.

## Results (p50/p95/p99 in ms; statuses show the full response mix)

### Public endpoints (rate-limited by design; 429 = limiter working, included honestly)
| endpoint | c=10 | c=50 | c=100 | c=200 |
|---|---|---|---|---|
| GET /api/public/clinics | 28/52/89 | 116/235/896 | 221/316/1796 | 316/523/6318 |
| GET /api/public/slots (250k appts) | 60/82/- | 256/390/1094 | 531/754/780 | 959/2215/5735 |
- pub-clinics 200-response throughput ~250-340 rps; the 429 share grows with per-user rate (limiter: 120/min/IP).
- pub-slots is 100% 200s (computeSlots is CPU/DB-bound so per-user rate stays under the cap). p50 degrades from 60ms (c=10) to 959ms (c=200) on 1 vCPU.

### Booking write path (POST /api/public/book, limiter 10/min/IP)
- First run (pre-fix): at c=100/200 the app returned raw 500s (12 and 56) — Prisma "Unable to start a transaction in the given time" under pool/lock saturation.
- FIX: bookAppointment now uses maxWait 10s and maps P2028/transaction-start failures to a clean 503 BOOKING_BUSY; verified: after the fix, c=100 and c=200 produced ZERO 500s (331 and 471 clean 409 slot conflicts on an exhausted slot set, p50 1.8s/3.1s queued on the per-doctor advisory lock).
- Successful bookings measured: 60 in 5s at c=10 before slot exhaustion (the per-IP 10/min cap and 80-slot test set bound this; the limiter is a deliberate anti-abuse control).

### Authenticated list endpoints (no limiter; 100% 200s, zero errors at every level)

## Findings
1. FIXED - Booking bursts on one doctor produced raw 500s (transaction start timeout). Now clean 409/503. Regression: full vitest 94/94 green after the change.
2. Known hotspot - /api/appointments day-range list (COUNT + includes over 251k rows) is the slowest endpoint: p50 3.6s at c=200 on 1 vCPU. Indexes (clinicId+startsAt, doctorId+startsAt, branchId+status+startsAt) are present; further improvement needs cursor pagination or dropping the exact COUNT, which is a product decision, not a defect. At c=10-50 (realistic single-clinic load) it serves 243ms-1.2s p50.
3. The in-memory rate limiter is per-process: correct for the single-instance Render deployment; multi-instance would need Redis (already noted in code comments).
4. Capacity context: all numbers are from a 1 vCPU/2GB sandbox. A Render starter instance has more CPU and RAM; do not quote these as production SLAs. Relative behavior (what degrades, where, and that nothing errors) is the meaningful result.

## Reproduce
npm run build; npx tsx scripts/bench-seed.mts clinics|gencsv|load|analyze|counts; npx tsx scripts/load.mts <endpoint> 10,50,100,200 5
Raw data: /tmp/bench/results.jsonl (per-level JSON records with environment).
